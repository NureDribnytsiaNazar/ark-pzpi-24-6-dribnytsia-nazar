2 ЗАВДАННЯ

Розробити клієнтську частину для IoT-пристрою програмної системи «Оберіг» (тема № 142 «Програмна система для безпеки житла») на основі серверної частини, створеної в лабораторних роботах № 2 і № 3:

– описати будову програмного забезпечення IoT-клієнта та побудувати UML-діаграму прецедентів;

– реалізувати бізнес-логіку вузла: фільтр брязкоту контактів, блокування повторних спрацювань PIR, локальний автомат режимів охорони, буфер подій, повтори зі зростаючою затримкою, перевірку підпису команд сервера й індикацію стану (вимоги ІК-1…ІК-7 з Vision & Scope);

– реалізувати функції налаштування вузла (ІК-8) та розширити серверну частину підписаними командами й конфігурацією вузла;

– побудувати UML-діаграму діяльності вузла;

– перевірити роботу вузла із сервером і задокументувати прийняті інженерні рішення;

– оформити звіт і завантажити код у репозиторій GitHub.

3 ОПИС ВИКОНАНОЇ РОБОТИ

3.1 Середовище та обсяг змін

Роботу виконано в репозиторії https://github.com/NureDribnytsiaNazar/oberih в окремій гілці lab4, відгалуженій від гілки lab3. Гілка містить 28 комітів. Прошивка лежить у каталозі iot, зміни сервера в каталозі server. Фрагменти коду в додатку Б мають постійні посилання на коміт 355bb6e (останній коміт гілки після виправлень за результатами ревю коду, розділ 3.10), тому рядки в них не зміщуються після подальших змін гілки.

Вузол написано мовою C++ для мікроконтролера ESP32 у середовищі PlatformIO з бібліотекою Arduino. Фізичної плати в роботі немає: вузол виконується в симуляторі Wokwi [5] у VS Code. Схема містить плату ESP32 DevKit C v4, два перемикачі геркона (двері й вікно), датчик руху PIR, перемикач тампера, RGB-світлодіод і зумер. Піни, канали й межі налаштувань зібрано в одному файлі iot/include/config.h.

У каталозі iot додано 49 файлів (3877 рядків), у каталозі server змінено 25 файлів (додано 1661 рядок, вилучено 37), у документації змінено 16 файлів. Серверна частина отримала міграцію 0004, підписані команди вузлу, зокрема команду конфігурації set_config, а також виконання розкладів постановки (міграція 0005, розділ 3.9). Кількість тестів сервера зросла з 146 до 175. Прошивка має 65 юніт-тестів у 9 наборах.

3.2 Будова програмного забезпечення IoT-клієнта

Логіку вузла відокремлено від платформи. Модулі першої групи в таблиці 1 не звертаються до Arduino API, тож їхні юніт-тести виконуються на ПК командою pio test -e native [6]. Для перевірки підпису команд довелося написати власну реалізацію SHA-256 і HMAC [1, 3]: підпис мав перевірятися тими самими тестами на ПК, що й решта логіки, без залежності від бібліотек платформи. Правильність реалізації перевіряється тестовими векторами RFC 4231 [2].

3.3 Цикл роботи вузла

Діаграму діяльності головного циклу NodeApp::loop наведено на рисунку А.2. Після запуску вузол читає з NVS налаштування, буфер, лічильник seq і останнє прийняте одноразове число, потім підключається до мережі Wokwi-GUEST. Далі цикл повторюється: консоль, контакти з фільтром брязкоту, PIR з блокуванням, таймери автомата, надсилання буфера, heartbeat, індикація.

Діаграму оновлено після живого запуску в Wokwi та після ревю коду, тож вона відповідає коду. Відмінностей від першої версії три. HTTPS-клієнт тримає одне з'єднання на всі запити (keep-alive), а не відкриває нове на кожен запит. Після підключення до Wi-Fi вузол пробує зв'язатися із сервером одразу, а не чекає завершення затримки повтору. Конфігурацію з відповіді heartbeat вузол бере лише з підписаної команди set_config, а поле config не застосовує зовсім (розділ 3.10). Поведінку в коді відображає лістинг Б.14.

3.4 Математична обробка даних

Логіка вузла складається з кількох невеликих алгоритмів над потоком сигналів датчиків. Нижче описано кожен із них. Усі часові величини беззнакові 32-бітні, а інтервали обчислюються різницею значень millis(), тож вони коректні й після переповнення лічильника (приблизно через 49 діб роботи).

3.4.1 Фільтр брязкоту контактів (ІК-2)

Механічний контакт при перемиканні кілька мілісекунд передає серію хибних змін стану. Фільтр (лістинг Б.1) тримає стабільний стан s і кандидата c з моментом його появи t(c). Зміна стану приймається, коли кандидат утримується не менше за T(d):

s := c, якщо c ≠ s і t − t(c) ≥ T(d) (1)

де s – поточний стабільний стан контакту;

c – останній прочитаний стан, що відрізняється від стабільного;

t(c) – момент, коли кандидат з'явився вперше;

T(d) – інтервал фільтрації, налаштування debounce_ms, 10–1000 мс, за замовчуванням 50 мс.

Якщо брязкіт повернув контакт у стабільний стан, кандидата скасовано, а відлік починається знову. Для перевірки використано режим sim bounce, який за 45 мс робить 9 перемикань контакту: події при цьому не виникає (журнал: [debounce] ch1: 9 toggles in 45 ms, accepted changes 0).

3.4.2 Блокування повторних спрацювань PIR (ІК-3)

Датчик руху під час руху людини видає серію імпульсів. Спрацювання приймається, якщо від попереднього прийнятого минув час блокування T(b) (лістинг Б.2):

accept(t) = істина, якщо немає t(0) або t − t(0) ≥ T(b) (2)

де t(0) – момент попереднього прийнятого спрацювання;

T(b) – налаштування pir_lockout, 0–600 с, за замовчуванням 10 с.

Значення 0 вимикає блокування. Відхилені спрацювання не змінюють t(0), тому безперервний рух не продовжує блокування нескінченно.

3.4.3 Автомат режимів (ІК-1)

Локальний автомат повторює таблицю переходів сервера (лістинг Б.3): шість режимів і сім тригерів. Постановка під охорону можлива лише зі стану disarmed, зняття доступне з будь-якого іншого стану, проникнення переводить режим охорони в затримку входу, а завершення затримок веде до armed_away або alarm. Датчик тампера та цілодобова зона дають тривогу негайно в будь-якому режимі. У режимі «Вдома» внутрішні зони й датчики руху не контролюються (функція is_monitored, лістинг Б.4). Нульова затримка пропускає проміжний стан: постановка за нуля секунд одразу веде до armed_away, а проникнення до alarm.

На відміну від сервера, вузол не обчислює індекс достовірності: будь-яке спрацювання контрольованої зони він вважає проникненням. Зі значеннями за замовчуванням сервер поводиться так само, бо вага одного датчика (0,4–0,5) не менша за поріг тривоги 0,4 (припущення 48). Режим вузол змінює лише двома способами: за своїми таймерами й датчиками та за підписаною командою сервера. Кнопки зняття з охорони на вузлі немає: сервер лишається джерелом істини про режим (припущення 37).

3.4.4 Буфер подій (ІК-4)

Події зберігаються в кільцевому буфері на 64 записи. Кожна подія отримує номер seq, що зростає на одиницю, і час за годинником вузла. Знімок буфера записується в NVS при кожній зміні (лістинг Б.5), тож події переживають перезавантаження. До першої синхронізації годинника події чекають на час: пакет не надсилається, поки в найстарішої події немає мітки часу, щоб порядок не порушувався. Події з попереднього запуску після синхронізації отримують її момент і позначку approx_time (лістинг Б.6).

Коли буфер заповнено, для нової події вилучається найстаріша нетривожна подія; якщо тривожні всі, вилучається найстаріша (лістинг Б.7). Тривожною вважається подія, що перевела автомат у затримку входу чи тривогу, і будь-яка подія тампера (припущення 44). Пакет містить до 20 подій, хоча сервер приймає до 200.

Окремий випадок: Wokwi починає кожен запуск з чистої флеш-пам'яті, тож лічильник seq почався б з одиниці, а сервер вважав би такі події дублікатами. У відповіді heartbeat сервер повертає last_seq вузла; якщо цей номер більший за лічильник вузла, ще не надіслані події отримують номери після нього (метод adopt_server_seq, припущення 45). На справжній платі лічильник зберігається в NVS, і це правило не спрацьовує.

3.4.5 Повтори зі зростаючою затримкою (ІК-5)

Після невдалої спроби надіслати пакет чи heartbeat вузол чекає, а потім повторює. Затримка перед n-ю повторною спробою (лістинг Б.8):

d(n) = min(b · 2^n, d(max)) + j, j ∈ [0; 250] мс (3)

де b – базова затримка, 1 с;

n – кількість попередніх невдалих спроб підряд;

d(max) – верхня межа, 60 с;

j – випадкова добавка (джитер), яку дає генератор xorshift32 [9] із фіксованим початковим значенням.

Послідовність без добавки така: 1, 2, 4, 8, 16, 32, 60, 60 с і далі. Добавка потрібна, щоб кілька вузлів, які втратили зв'язок одночасно, не повторювали запити в один момент [8]. Фіксоване початкове значення робить тести детермінованими. Множення виконується в 64 бітах, щоб b · 2^n не переповнило 32-бітне число.

Відповідь сервера класифікує функція classify_response. Коди 2xx означають доставку. Помилки з'єднання, 5xx, 408 і 429 повторюються без втрати подій. Коди 401 і 403 повторюються раз на 60 с, бо токен міг бути відкликаний тимчасово. Інші 4xx (наприклад, невідомий канал) вважаються відхиленням пакета: після трьох спроб пакет відкидається із записом у журнал, щоб один некоректний пакет не блокував чергу назавжди (лістинг Б.15). Невдалі heartbeat теж повторюються за формулою (3), а після трьох поспіль вмикається індикація втрати зв'язку (N(проп.) = 3).

3.4.6 Перевірка підпису команд (ІК-7)

Команди сервера (постановка, зняття, нова конфігурація) змінюють стан охорони, тому вузол перевіряє їх незалежно від каналу зв'язку. Підпис обчислюється як HMAC-SHA256 [1, 3] над рядком з п'яти полів:

σ = HMAC-SHA256(K, node_id | nonce | type | payload | issued_at) (4)

де K – ключ підпису вузла, 32 байти, відомий серверу й вузлу;

node_id – ідентифікатор вузла;

nonce – одноразове число команди;

type – тип команди (arm_away, arm_home, disarm, set_config);

payload – корисне навантаження, рядок канонічного JSON;

issued_at – момент видачі команди, секунди Unix.

Лістинг Б.9 виконує перевірки в такому порядку: підпис (порівняння сталого часу, щоб тривалість порівняння не розкривала правильних байтів); синхронізація годинника вузла із сервером; свіжість команди за умовою (5); одноразове число. Підроблена команда відхиляється першою перевіркою й не впливає ні на що інше.

|t(вузла) − issued_at| ≤ 60 с і nonce > nonce(останнє) (5)

де t(вузла) – поточний час вузла за server_epoch із останнього heartbeat;

nonce(останнє) – останнє прийняте одноразове число, збережене в NVS.

Повторно надіслана команда з тим самим nonce не виконується вдруге. Час вузла береться тільки з server_epoch: годиннику ESP32 до синхронізації вузол не довіряє, а NTP не потрібен (припущення 47). Отримання підтверджується для кожної команди, зокрема відхиленої, інакше сервер видавав би її знову й знову.

3.4.7 Індикація (ІК-6)

Функція indicator_state (лістинг Б.11) повертає стан трьох світлодіодів і частоту зумера за режимом, станом зв'язку й часом. Режим disarmed горить зеленим, armed_home червоним і зеленим разом, armed_away червоним. Затримки виходу й входу блимають червоним із періодом 500 мс, тривога блимає з періодом 200 мс і вмикає тон 2000 Гц. Втрата зв'язку вмикає синій спалах поверх кольору режиму й короткий сигнал кожні 10 с, а після відновлення синій горить 3 с.

3.5 Взаємодія вузла із сервером

3.5.1 Протокол обміну

Вузол використовує два ендпоінти, що вже були на сервері: POST /device/heartbeat і POST /device/events. Автентифікація виконується токеном пристрою в заголовку X-Device-Token, обмін ведеться з HTTPS. Heartbeat вузол надсилає з інтервалом poll_interval (за замовчуванням 30 с). У запиті він повідомляє версію прошивки, поточний режим, версію конфігурації, глибину буфера та ідентифікатори підтверджених команд. У відповіді сервер повертає свій час (server_epoch), режим об'єкта, інтервал опитування, останній відомий номер seq вузла й відкриті команди (лістинг Б.20). Поле config з конфігурацією вузла у відповіді лишилося для зворотної сумісності, але вузол його не застосовує.

Послідовність від команди користувача до підтвердження вузлом показано на рисунку А.3. Користувач викликає зміну режиму через API, сервер ставить підписану команду в чергу вузла, а вузол отримує її з наступною відповіддю heartbeat, перевіряє, виконує й підтверджує в наступному запиті.

3.5.2 Зміни серверної частини

Для підписаних команд і налаштувань вузла додано міграцію 0004 (рисунок А.4); міграція 0005 додає поле schedules.last_run_at. До налаштувань об'єкта додано поля debounce_ms і pir_lockout_s та версію конфігурації config_version. До вузла додано поле command_key (32 випадкові байти). Нова таблиця node_commands зберігає чергу команд: тип, корисне навантаження, одноразове число, моменти видачі, доставки, підтвердження й закінчення строку дії та стан (pending, delivered, acked, expired).

Команда має строк дії 60 с і видається в кожній відповіді heartbeat, доки вузол її не підтвердить або строк не мине (лістинг Б.19). Одноразове число дорівнює більшому з (останнє + 1) і поточного часу сервера в мілісекундах (лістинг Б.18), тому воно зростає навіть після очищення бази, а вузол зберігає останнє прийняте число в NVS. Число обчислюється під блокуванням рядка вузла (SELECT … FOR UPDATE), тож дві паралельні команди не отримують однакового значення. Корисне навантаження передається рядком канонічного JSON, щоб вузол перевіряв підпис над отриманими байтами без повторної серіалізації (припущення 39).

Крім постановки й зняття з охорони, сервер узгоджує режим після автономної роботи вузла. Якщо в heartbeat вузол повідомляє режим, що відрізняється від режиму об'єкта, буфер вузла порожній і відкритої команди немає, сервер ставить команду до свого режиму. Поки в буфері є події, розбіжність не усувається, бо це може бути ще не доставлена тривога (припущення 37). Режими exit_delay і armed_away вважаються узгодженими, затримку входу й тривогу сервер вузлу не нав'язує. Якщо вузол підтвердив команду узгодження, а стан не змінився (наприклад, вузол відхиляє підпис після повторного введення без перепрошивки), така сама команда повторюється не частіше ніж раз на 5 хв (лістинг Б.21, припущення 41а). Підтверджені й прострочені команди, старші за 30 днів, видаляє очищення застарілих даних.

Конфігурація вузла надходить лише підписаною командою set_config. Вузол застосовує її цілком і лише з більшою версією (лістинг Б.12). Якщо вузол пропустив команду (строк дії 60 с минув або NVS очищено), він повідомляє в heartbeat меншу версію, і сервер ставить підписану set_config повторно (функція reconcile_config, лістинг Б.19). Під час введення вузла в експлуатацію версія конфігурації стає не меншою за поточний час Unix, тож після очищення чи відновлення БД сервера вузол знову приймає конфігурацію (припущення 42). Спочатку конфігурація надходила ще й полем config відповіді heartbeat без підпису; ревю коду показало, що так можна змінити затримки без підпису (затримка входу 600 с фактично вимикає реакцію на проникнення), і цей шлях прибрано.

Ключ підпису вузол отримує разом із токеном один раз під час введення вузла в експлуатацію: скрипт server/scripts/provision_node.py записує адресу сервера, ідентифікатор, токен, ключ і сертифікат у файл iot/include/secrets.h, який вбудовується в прошивку й не потрапляє в git. Сервер зберігає ключ у базі відкрито, бо ним підписує. Це свідомий компроміс, альтернативою є асиметричний підпис (припущення 38).

3.5.3 Захист каналу

Вузол з'єднується із сервером за HTTPS [4]: клас WiFiClientSecure перевіряє сертифікат сервера за вбудованим якорем довіри. Під час живого запуску в Wokwi виявилося, що повне рукопожаття TLS на ESP32 у симуляторі триває 8–11 с, а з кореневим сертифікатом понад 18 с, після чого сервер рве з'єднання. Тому якорем довіри обрано безпосереднього видавця сертифіката сервера, а не корінь (припущення 50). Ціна рішення: коли провайдер змінить проміжний сертифікат, треба повторити provision_node.

Щоб не виконувати повне рукопожаття на кожен запит, HTTPS-клієнт тримає одне з'єднання з HTTP keep-alive (лістинг Б.17). У симуляторі три heartbeat виконуються з одним рукопожаттям, а окремий запит триває близько 215 мс. Кількість рукостискань показує консольна команда status (припущення 50а).

Публічної адреси сервер у Wokwi не має: публічний шлюз симулятора дає лише вихідні з'єднання, а адреса host.wokwi.internal працює тільки з приватним шлюзом платного тарифу [5]. Тому сервер відкрито через TCP-тунель bore (bore.pub). Тунель Cloudflare Quick Tunnel не підійшов: він сам завершує TLS і рвав рукопожаття з Wokwi стабільно через 11,4 с (чотири спроби поспіль). У підсумковій схемі TLS завершує власний сервер (uvicorn із самопідписаним сертифікатом RSA-2048), тунель лише пересилає байти, а вузол довіряє цьому сертифікату (припущення 50б). Перевірка TLS при цьому лишається справжньою; режим без перевірки є тільки в окремому середовищі збирання esp32dev_devtls для розробки.

3.6 Функції налаштування

Через Bluetooth Low Energy налаштування вузла, як вимагає Vision & Scope, зробити не вдалося: Wokwi не емулює Bluetooth (ЗЛ-1). BLE-коду в роботі немає, а налаштування доступні двома шляхами (припущення 49).

Перший шлях: консоль у вікні Serial (лістинг Б.13). Команди get, set, save, defaults, status, buffer, net і sim описано в таблиці 3. Команда set перевіряє значення за межами з таблиці 4 і не зберігає зміну в NVS, поки не виконано save. Команда defaults повертає значення за замовчуванням, але лишає адресу сервера: її задано під час введення вузла, і втрата зробила б вузол недосяжним.

Другий шлях: налаштування із сервера. Затримки об'єкта (exit_delay, entry_delay, poll_interval) і параметри вузла (debounce_ms, pir_lockout) змінюються через API, після чого версія конфігурації зростає, а вузол отримує нову конфігурацію підписаною командою set_config. Межі для debounce_ms і pir_lockout у Vision & Scope не задано, тому їх обрано в роботі (припущення 43), а сервер перевіряє ті самі межі, що й вузол. Зміна з консолі діє до появи новішої версії із сервера; команда defaults скидає версію до нуля, і сервер надсилає свою конфігурацію знову (припущення 42).

3.9 Виконання розкладів постановки

Під час аналізу проєкту виявилося, що розклади постановки на охорону (таблиця schedules, API, експорт та імпорт, ЛБ2 і ЛБ3) лише зберігалися, а фоновий виконавець їх не запускав. У цій гілці прогалину закрито. Тепер кожен прохід timers.process_timers викликає schedules.run_due_schedules (припущення 59). Розклад спрацьовує, коли місцевий час об'єкта досяг local_time у день із маски days_mask. Момент запуску записується в поле schedules.last_run_at (міграція 0005), тож той самий запуск не повторюється.

Правила виконання такі. Пропущений запуск, старший за 10 хв, не наздоганяється: сервер міг бути вимкнений, або розклад створено на вже минулий час. Зняття за розкладом не виконується в режимах entry_delay і alarm, щоб не заглушити проникнення. Постановка, коли об'єкт уже під охороною, пропускається. Зміна режиму пишеться в журнал охорони з джерелом schedule, а вузли об'єкта отримують підписану команду. Запуск о 23:58, який виконавець побачив уже після півночі, належить попередньому дню маски. Час порівнюється в UTC, тож у дні переведення годинника вікно рахується в реальних хвилинах, а неіснуючий час весняного переходу (03:30) настає на годину пізніше, а не губиться. Логіку перевіряють 9 тестів у test_schedule_runs.py; вживу в Wokwi виконання розкладів не показували.

3.11 Обмеження

– Прошивку перевірено лише в симуляторі Wokwi, на справжній платі ESP32 її не запускали. Поведінка радіомодуля, живлення й реальних датчиків не перевірена.

– Збереження в NVS між перезавантаженнями перевірено тестом на підставному сховищі: у Wokwi кожен запуск починається з чистої флеш-пам'яті.

– Прострочену команду й повторний nonce перевірено юніт-тестами вузла й серверними тестами. Вживу це видно лише побічно: команда set_config версії 2 отримала стан expired, коли симуляція стояла на паузі. Переповнення буфера (64 події) перевірено лише тестом.

– BLE не реалізовано (ЗЛ-1). Wokwi CLI й автоматичний сценарій не додано: потрібен токен WOKWI_CLI_TOKEN.

– Рукопожаття TLS у Wokwi триває 8–11 с, тож перший запит після запуску чи обриву повільний. Тунель bore.pub є публічним сервером без гарантій доступності, а його порт змінюється з кожним запуском; тоді треба повторити provision_node і зібрати прошивку.

– Ключ підпису команд зберігається в БД відкрито, а Flash заповнено на 90,7 %. Якір довіри TLS потребує оновлення, коли змінюється проміжний сертифікат.

– Виконання розкладів постановки перевірено лише тестами, вживу воно не показувалось. Атаку з підміною поля config вживу не відтворювали (розділ 3.10).

4 ВИСНОВКИ

У результаті виконання лабораторної роботи розроблено IoT-клієнт «Оберіг» для ESP32: вузол читає геркони, PIR і тампер, фільтрує брязкіт контактів і повторні спрацювання PIR, веде локальний автомат режимів, накопичує події в буфері в пам'яті NVS, надсилає їх на сервер із повторами зі зростаючою затримкою та перевіряє підписані команди сервера. Вимоги ІК-1…ІК-8 реалізовано, окрім передачі налаштувань через BLE, яку замінено консоллю й конфігурацією із сервера.

Логіку вузла відокремлено від платформи, тож її перевіряють 65 юніт-тестів на ПК. Серверна частина отримала підписані команди (HMAC-SHA256, строк дії 60 с, одноразове число), конфігурацію вузла з версією та міграцію 0004; кількість тестів сервера зросла з 146 до 175. Прошивка збирається без попереджень, займає 90,7 % Flash і 17,5 % RAM.

Вузол перевірено вживу в симуляторі Wokwi за повним сценарієм демонстрації. Це виявило сім дефектів у платформному шарі, який юніт-тести на ПК не охоплюють. Найвагоміші стосуються TLS: повне рукопожаття на ESP32 у симуляторі триває 8–11 с, тож довелося замінити кореневий якір довіри на сертифікат видавця, тримати одне з'єднання keep-alive та відмовитися від тунелю, що сам завершує TLS.

Відомі обмеження: перевірка лише в симуляторі, відсутність BLE, ключ підпису в БД у відкритому вигляді, залежність демонстрації від тунелю bore.pub. Додатково закрито прогалину попередніх робіт: розклади постановки на охорону тепер виконує фоновий виконавець, але перевірено це лише тестами. Ревю коду знайшло сім недоліків, найважливіший з яких дозволяв змінити налаштування вузла без підпису; усі виправлено, а конфігурація тепер надходить лише підписаною командою.

Наступним етапом (лабораторна робота № 5) є розгортання системи в Docker з Nginx і демонстрація її роботи разом із вузлом.

1 void hmac_sha256(const uint8_t* key, size_t key_length, const uint8_t* message,

2 size_t message_length, uint8_t digest[kSha256DigestBytes]) {

3 uint8_t block_key[kHmacBlockBytes] = {};

4 if (key_length > kHmacBlockBytes) {

5 Sha256 key_hash;

6 key_hash.update(key, key_length);

7 key_hash.finish(block_key);

8 } else {

9 std::memcpy(block_key, key, key_length);

10 }

11 uint8_t pad[kHmacBlockBytes];

12 for (size_t i = 0; i < kHmacBlockBytes; ++i) {

13 pad[i] = block_key[i] ^ kInnerPad;

14 }

15 uint8_t inner_digest[kSha256DigestBytes];

16 Sha256 inner;

17 inner.update(pad, sizeof(pad));

18 inner.update(message, message_length);

19 inner.finish(inner_digest);

20

21 for (size_t i = 0; i < kHmacBlockBytes; ++i) {

22 pad[i] = block_key[i] ^ kOuterPad;

23 }

24 Sha256 outer;

25 outer.update(pad, sizeof(pad));

26 outer.update(inner_digest, sizeof(inner_digest));

27 outer.finish(digest);

28 }

30 std::string to_hex(const uint8_t* data, size_t length) {

31 std::string hex;

32 hex.reserve(length * 2);

33 for (size_t i = 0; i < length; ++i) {

34 hex.push_back(kHexDigits[data[i] >> 4]);

35 hex.push_back(kHexDigits[data[i] & 0x0F]);

36 }

37 return hex;

38 }

40 bool from_hex(const std::string& hex, uint8_t* out, size_t out_length) {

41 if (hex.size() != out_length * 2) {

42 return false;

43 }

44 for (size_t i = 0; i < out_length; ++i) {

45 const int high = hex_value(hex[2 * i]);

46 const int low = hex_value(hex[2 * i + 1]);

47 if (high < 0 || low < 0) {

48 return false;

49 }

50 out[i] = static_cast<uint8_t>((high << 4) | low);

51 }

52 return true;

53 }

55 bool constant_time_equal(const std::string& left, const std::string& right) {

56 if (left.size() != right.size()) {

57 return false; // довжина підпису не секретна

58 }

59 uint8_t difference = 0;

60 for (size_t i = 0; i < left.size(); ++i) {

61 difference |= static_cast<uint8_t>(left[i] ^ right[i]);

62 }

63 return difference == 0;

54 db.execute(select(Node.id).where(Node.id == node.id).with_for_update())

55 last = db.scalar(

56 select(func.max(NodeCommand.nonce)).where(NodeCommand.node_id == node.id)

57 )

58 nonce = max((last or 0) + 1, int(now.timestamp() * 1000))

59 command = NodeCommand(

60 node_id=node.id,

61 command_type=command_type,

62 payload=payload,

63 nonce=nonce,

64 issued_at=now.replace(microsecond=0),

65 expires_at=now.replace(microsecond=0) + COMMAND_TTL,

66 status=CommandStatus.PENDING,

67 )

68 db.add(command)

69 db.flush()

70 return command
